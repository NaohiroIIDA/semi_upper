# 既知の問題・注意点

コードを読んで見つかった、仕様とのズレや挙動上の注意点です（2026-10-15 時点、未修正）。

## 1. 角度の2バイト結合が ×255

- ファームウェア（[main.cpp](../STM32duino/src/main.cpp) の `canRead()`）: `tgt = 下位 + 255 * 上位`
- Python（[send_once_args.py](../python/send_once_args.py)）: `上位 = n >> 8`, `下位 = n & 0xFF`（×256 前提）
- 返信（`set_candata()`）は `highByte/lowByte` を使うので ×256 です。

**影響**: 256°以上を指定すると 1° 小さく解釈されます（例: 300° → 299°）。不感帯（±5°）の範囲に収まるので
実用上は目立ちませんが、ファーム側を `(m1 << 8) | m2` に直すのが本来の形です。

## 2. `send_once_args.py` のデフォルト ID が 0x69

デフォルトの `--id` が `0x69`（マイコンの**送信** ID）になっています。マイコンが受け付けるのは `0x6A` です。
**`--id 0x6a` を必ず指定してください**（README の例はそうなっています）。

## 3. 軸番号とモータ端子が交差している

`motor_cmd(ch, …)` は `ch=1` のとき M1 端子、`ch=0` のとき M2 端子を駆動します。そして `motor_work()` は

- エンコーダ1（CS1=PB0）の角度 → `motor_cmd(0, …)` → **M2 端子（PB4/PB5）**
- エンコーダ2（CS2=PB1）の角度 → `motor_cmd(1, …)` → **M1 端子（PA15/PB3）**

という対応です。回転方向の極性も軸ごとに逆になっています。配線に合わせて意図的にこうした可能性もありますが、
ピン名と実際の軸が一致しない点に注意してください。

## 4. 不感帯の定数が軸1にしか効かない

`MOTOR_DZ`（5）を使っているのは軸1だけで、軸2は `5` を直接書いています。値は同じですが、
`MOTOR_DZ` を変えても軸2には反映されません。

## 5. 移動平均が 0°/360° の境界で破綻する

生値（0〜16383）をそのまま算術平均しているので、磁石が 0° 付近を行き来すると平均値が 180° 付近になります。
その結果、モータが誤った方向に回る可能性があります。可動範囲が 0° をまたがないように取り付けてください。

## 6. 制御ループが遅く、応答が遅れる

`readRegister()` の中に `delay(10)` が2回あり、2軸で 1 ループ **約 40ms 以上** かかります（ほかに UART 出力もあります）。
30 サンプルの移動平均と合わせると、角度の反映は **約 1.2 秒遅れ** ます。オーバーシュートの原因になりえます。

## 7. モータ制御は ON/OFF のみ

駆動ピンはデジタル出力（HIGH/LOW）だけで、PWM による速度制御はしていません。
目標との差が 5° 以上なら全速、5° 未満なら停止です。

## 8. 割り込みハンドラ内でシリアル出力している

`canISR()` で `Serial2.print` を呼んでいます。受信が多いと割り込み処理が長くなります。
また受信バッファは1フレーム分しかないので、ループ1周の間に複数フレームが届くと、最後のフレーム以外は失われます。

## 9. コメントと実装の食い違い

`setup()` の `can.begin(...)` のコメントは「250k bit rate, no transceiver chip」ですが、実際は
**500kbps・トランシーバあり（`PORTA_11_12_XCVR`）** です。

## 10. Python ツールは Linux 専用

SocketCAN（`interface="socketcan"`）と `termios`/`tty` を使っているので、Linux 以外では動きません。
